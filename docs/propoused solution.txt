# ICS and USB port changes: review

I haven't run any of this against your machine, so treat the Windows internals below as informed hypotheses to test. I've ranked them by how well they fit your evidence.

## Summary

Your two symptoms, "different port fails, same port works" and "private enable fails even on the Hyper-V switch", point to the same cause. The adapter's identity is derived from the port, and the old identities leave behind state that blocks ICS globally. Fixing the identity on the console side avoids the whole class of problem.

## 1. The root cause is probably the missing USB serial number

Your instance IDs look like `USB\VID_0525&PID_A4A2\5&1134133F&0&1`, `...&0&2`, `...&0&3`. That `5&<hash>&0&<port>` form is what Windows generates for a device that reports no `iSerialNumber`. Windows can't tell two plugs of the device apart, so it keys the device instance on the hub and port. A new port means a new PnP device, a new `NetCfgInstanceId` GUID, a new "Ethernet N" name and a new ghost left behind. That also answers your Q4. Resolving by GUID helps with renames, but each port really is a new identity to ICS, and no client-side lookup changes that.

**Fix:** give `g_ether` a serial number and a fixed host MAC. The module accepts both as parameters, which is a one-line change to the modprobe options or load script:

```
modprobe g_ether iSerialNumber=G350-0001 host_addr=02:xx:xx:xx:xx:xx dev_addr=02:yy:yy:yy:yy:yy
```

With a serial number, Windows keys the instance on VID, PID and serial, so the device is one adapter on every port, with the same GUID and name. This isn't a rewrite of your addressing scheme, so it should fit your console-side constraint. I'm fairly confident `iSerialNumber` is accepted by the 4.4 composite gadget, but verify it with `modinfo g_ether` on the device. Expect one more new adapter the first time after the change, and the ghosts stop accumulating after that.

## 2. A likely cause of the global `0x80040201`: ghost adapters still own the addresses

`0x80040201` is `EVENT_E_ALL_SUBSCRIBERS_FAILED`. It's a generic COM+ event-system wrapper, so it hides the real failure. ICS needs to assign `192.168.137.1` to the private adapter. Your app adds `192.168.137.1` and `192.168.7.1` as manual addresses on every console adapter. Each ghost adapter therefore keeps those addresses in its registry config. Windows treats a static IP held by an absent adapter as a conflict, which is the classic "address already assigned to another adapter" error. If that is happening, private enable fails on any adapter, including the Hyper-V switch, because ICS can't claim the scope address. The two kinds of evidence you have (ghosts present, global failure) are consistent with this.

Cheap tests, in order:

1. Check Event Viewer for hints, in System (source `SharedAccess_NAT` or tcpip) and in `Applications and Services Logs > Microsoft > Windows`. An IP conflict event around the failure would confirm this.
2. Show hidden devices in Device Manager, or run `pnputil /enum-devices /class Net /disconnected`, and remove the ghost RNDIS entries (`pnputil /remove-device <InstanceId>`). Then retry private enable.
3. Make sure `EventSystem` and `SENS` are running, since the event system is the failing layer.

Also test the baseline you flagged: reboot with `ScopeAddress` intact and retry before any deeper work. I agree that's the cheapest experiment.

## 3. Answers to your numbered questions

**Q1.** I'm not aware of a documented limitation, and there's no official "re-register adapter" API. The identity-plus-ghost explanation above covers the behaviour without needing one.

**Q2.** Yes, `EnumEveryConnection` is backed by the connection entries in the registry, and ghost entries can surface. Filter on `INetConnection.GetProperties().Status`. Absent hardware reports `NCS_HARDWARE_NOT_PRESENT` (4 in the `NETCON_STATUS` enum, if I remember the values correctly; check against `netcon.h`). Cross-check the GUID against `Get-NetAdapter` or `GetAdaptersAddresses`, and prefer connected or media-disconnected over not-present.

**Q3.** I can't confirm a hard prerequisite list. Two things are worth trying:
- Strip the manual `192.168.137.1` and `192.168.7.1` from the private adapter before enabling, let ICS assign `.137.1` itself, then re-add `192.168.7.1` afterwards. ICS reconfigures the private adapter's addressing, and your pre-existing manual addresses on top may interfere.
- Don't worry about DHCP, IPv6 or NetBIOS first. They're unlikely to be the issue, and your tests already showed it failing on unrelated adapters.

**Q5, call order.** Most working ICS scripts enable **public first, then private**, after clearing existing sharing. Your code does private first. I'd flip it, which is a trivial test. A fresh `HNetShare` instance per operation is harmless and worth doing. Restarting `SharedAccess` or toggling the adapter is a plausible workaround, but it papers over the identity problem.

**Q6, virtual adapter in front.** I'd avoid it. The reasons:
- Bridging RNDIS is fragile because the bridge member's carrier drops on unplug.
- ICS on top of a bridge, a loopback or the Hyper-V Default Switch is a poorly supported combination. The Default Switch is managed by Hyper-V's own networking and conflicts with ICS.
- It adds moving parts without fixing the cause.

With the serial number fix, the stable-adapter design is unnecessary.

## Suggested order of work

1. Reboot and retest with `ScopeAddress` intact. Swap to public-then-private order.
2. Remove the ghost RNDIS devices and retest.
3. Remove manual addresses from the private adapter before enabling, then re-add `192.168.7.1`.
4. Set `iSerialNumber` and fixed MACs on the console. This should remove the port-move failure.
5. Keep `New-NetNat` as the fallback only if the first four fail.
